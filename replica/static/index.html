          what it keeps
          
    
          a replica starts with a face and a place in the family. the rest comes from its host. tell it a question and
      an answer, then ask again. what it remembers becomes part of its public record. this is a small memory you
      can add to, rather than a conversation with an all-knowing assistant.
          
    
          the journal is the part that wanders. when a replica makes a copy, some of its parent's words survive and
      some change along the way. the family tree keeps track of where each copy came from.
          

    
          what REA does here
          
    
          REA supplies the software inspection. Replica's own
      standalone specialists bring the inspection evidence back to your replica. On this site, the inspection agent runs on a separate worker;
      optional local build specialists can assemble supported results and run their tests.
      they use no language model or upstream agent service. a task outside their scope receives a clear decline.
          
    
          in our example, REA examined the source of a small notes app. the question was simple: how does its search
      find a note, order the matches and handle filters? the findings supported a reviewed reconstruction of that search.
      a second version kept the original search code and added a way to find several words and limit the results.
          
    
            
      
          1. investigate. REA gathers observations and source evidence.
            2. 
      
          2. build and check. an admitted local specialist assembles a supported implementation and runs its checks.
            3. 
      
          3. review and keep. the host decides what should become part of their replica's public record.
            4. 
      
          4. pass it on. approved skill packages preserve the files and their history
        so a descendant can extend the work.
            5. 
    
          
    
          run REA here. connect the wallet that hosts your replica and open “investigate with REA”.
      choose the included notes-search sample or upload one JavaScript or TypeScript source file, enter your question,
      approve sending the file and choose “run REA”. your replica queues the inspection and brings the findings back to this page.
      no installation, local runner or model-provider account is needed.
          
    
          this website action uses real REA to inspect source structure, module format and export relationships.
      it handles one UTF-8 source file up to 256 KB. it does not execute your uploaded program, inspect a whole repository
      or generate an arbitrary application. its evidence describes what was inspected; it may not answer a question about runtime behavior.
          
    
          findings stay private until you review one and choose “remember this reviewed finding”.
      saving publishes its question, answer and source evidence to your replica's record. uploaded source is deleted after processing;
      private inspection results are retained for up to 24 hours. each replica can run one inspection at a time, up to 20 per day.
          
    
          you can also import an existing REA finding: connect the hosting wallet, open
      “teach it a REA finding”, choose the finding file, read the preview, then choose “remember this reviewed finding”.
      its question, answer and source become public when saved.
          
    
          for files you want to keep on your computer, the optional Replica Runner is under
      “advanced: inspect private files on your own computer”. it also supports the small build tasks below, with local approval and tests.
          
    
          the first build capabilities are deliberately small: a single arithmetic helper, the included notes search, and an extension
      of a reviewed search parent. each replica has its own agent identity and a local profile choosing its specialists. adding broader capabilities requires new code and checks.
          
    
          REA and the specialists run outside this page. opening the site does not give them access to your
      files or start an investigation. evidence helps someone check a finding; it does not guarantee the finding is correct.
          

    
          what a copy can inherit
          
    
          we want it to inherit useful work as well as words. investigate something, build a small working version,
      test it, and keep the files together. a descendant should be able to start there, make a change and show
      what still works.
          
    
          the first example is a search tool for a small collection of
      notes. the first version searches titles and text. the descendant adds a search for all the words you
      entered and a limit on the number of results. the saved packages include the code, evidence and test results.
          
    
          the distinction matters: a journal can change as it travels. a saved piece of code and its evidence must
      arrive intact. new work gets a new version, with a link back to the one it grew from.
          
    
          skill packages preserve the saved files; the host still reviews them before use. the runner inspects only a
      source file selected locally. builds and tests start only after local approval; copied skills do not grant execution permissions.
          

    
          the host still decides
          
    
          a copy begins with an invitation. the other wallet chooses whether to accept. saving a finding is another
      choice. do not put private material in a replica's public memory.
          
    
          inheriting work should never mean inheriting access to somebody's computer. skill packages
      carry the work and its history; each host still decides what to inspect, change or run.
          
  
          

  
          
    
          a skill that survives copying
          
    
          the journal may change as it travels. this piece of work should not. the search example keeps its code,
      source evidence and tests in one downloadable package. the descendant reuses the parent's search file
      unchanged, adds its own work, and records which version it started from.
          
    
          the first version passed 20 recorded checks. the descendant passed 35, including checks that the earlier
      behavior still works. you can try both versions, read the evidence and download the files without a wallet.
